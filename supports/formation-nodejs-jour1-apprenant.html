Du JavaScript côté serveur

Pourquoi du JavaScript côté serveur

Le concept

Un restaurant. Premier modèle : chaque client a son serveur attitré, qui reste planté devant la cuisine tant que le plat n'est pas prêt ; il ne fait rien, mais il est occupé. Cent clients, cent serveurs. C'est le serveur web classique : un fil d'exécution (thread) par connexion, qui attend une base de données ou un fichier en occupant de la mémoire. Second modèle, Node.js : un seul serveur, qui transmet la commande en cuisine et va prendre celle de la table suivante pendant que le plat cuit ; quand la cuisine sonne, il revient servir.

Node.js exécute du JavaScript en dehors du navigateur, avec un principe : ne jamais attendre. Il demande une lecture de fichier ou une réponse réseau, passe à la suite, puis exécute la fonction qu'on lui a donnée quand le résultat arrive. Cette fonction s'appelle un callback (ce n'est pas une promesse : les promesses arrivent cet après-midi). Node.js est donc fait pour les applications qui attendent beaucoup : API, temps réel, et TaskFlow.

Pourquoi JavaScript ? Un seul langage du navigateur au serveur, le JSON comme format commun, du code partagé, et npm (plus de deux millions de paquets). Même langage ne veut pas dire même environnement : côté serveur, pas de window ni de document, mais les fichiers, le réseau et les processus. Node.js a été présenté par Ryan Dahl en 2009 ; sa documentation : nodejs.org/docs.

Dans la vraie vie : tous les jours ; beaucoup d'API web et presque tous les outils du développement web (npm, Vite, ESLint) tournent sur Node.js.

Architecture : V8, libuv et API Node.js

Le concept

Reprenons le restaurant : le serveur unique, c'est le fil qui exécute votre JavaScript ; la cuisine, ce sont les briques qui travaillent pendant qu'il continue.

  • V8, le moteur JavaScript de Chrome : il compile votre code en code machine et l'exécute ; seul, il ne sait ni lire un fichier ni ouvrir une connexion.
  • libuv, une bibliothèque écrite pour Node.js : elle tient la boucle d'événements, confie le réseau au système et le reste (fichiers, DNS, chiffrement, compression) à un groupe de 4 threads, puis prévient quand c'est fini.
  • L'API Node.js : les modules qu'on appelle dans le code, fs pour les fichiers, http pour le web, events pour les événements.

Un seul thread exécute votre JavaScript : « Node.js est monothread » est vrai pour votre code, faux pour le reste. Lire un fichier ne bloque pas le serveur ; un calcul de 2 secondes le bloque 2 secondes pour tout le monde. Pour utiliser plusieurs cœurs : plusieurs processus (cluster, jour 2) ou des worker_threads.

Dans la vraie vie : on ne touche jamais à V8 ni à libuv ; on en retient une règle : pas de gros calcul dans le serveur.

Quand choisir Node.js, versions et écosystème

Le concept

Un bon outil, c'est aussi un outil qu'on sait ne pas utiliser. Node.js excelle quand l'application attend beaucoup et calcule peu :

  • API REST ou GraphQL, temps réel (chat, notifications, WebSocket), outils en ligne de commande : adapté ;
  • calcul intensif (encodage vidéo, apprentissage automatique) : mal adapté, il bloque la boucle d'événements ; on confie ce travail à un worker ou à un autre service.

Versions. Chaque année, une version paire devient LTS (Long Term Support) : environ trois ans de correctifs ; c'est la seule qu'on met en production. En octobre 2026 : Node.js 22 reçoit les correctifs critiques jusqu'au 30 avril 2027, Node.js 24 est LTS jusqu'au 30 avril 2028, Node.js 26 devient LTS fin octobre 2026. À partir de Node.js 27, une seule version majeure sort chaque année, et toutes deviennent LTS. Le cours est écrit pour Node.js 22 et vérifié sous Node.js 24 : le code est le même.

Écosystème : npm (registre et gestionnaire de paquets) ; frameworks web : Express, Fastify, NestJS ; données : Sequelize, Prisma, Mongoose ; qualité : Mocha, Jest, node:test, ESLint.

Dans la vraie vie : à chaque nouveau projet ; on prend la LTS la plus récente et on fixe la version à trois endroits : .nvmrc (postes), engines dans package.json, image Docker (production).

Rappels JavaScript : portée, fermetures et this

Le concept

Côté serveur, on passe sans arrêt des fonctions à d'autres fonctions, qui les appellent plus tard : un callback à fs.readFile, un écouteur à un événement. Trois mécanismes décident de ce que la fonction voit à ce moment-là.

  • Portée : la zone du code où une variable existe. let et const vivent dans leur bloc { } : chaque tour de boucle a sa variable. var vit dans toute la fonction : une seule variable, partagée. Règle : const par défaut, let si la valeur change, jamais var.
  • Fermeture : une fonction emporte, comme dans un sac à dos, les variables de l'endroit où elle est née, même quand ce code est terminé. C'est ce qui permet à un callback appelé une seconde plus tard de retrouver ses variables.
  • this : l'objet devant le point au moment de l'appel. Avec service.presenter(), this vaut service ; passée seule en callback, la méthode perd son objet. call et apply imposent this pour un appel ; bind fabrique une fonction dont le this est fixé pour toujours. Une fonction fléchée n'a pas de this à elle : elle garde celui de l'endroit où elle est écrite.

La syntaxe moderne (ECMAScript 2015, dit « ES6 », et suivantes) utilisée pendant ces deux jours :

Syntaxe Exemple Version
const / let const PORT = 3000; ES2015
Fonction fléchée tasks.filter((t) => !t.done) ES2015
Chaîne modèle `Bonjour ${nom}` ES2015
Déstructuration const { done, q } = req.query; ES2015
Décomposition { ...task, done: true } ES2015 (objets : ES2018)
Classe, champ privé class TaskService { #tasks = new Map(); } ES2015, ES2022
async / await const data = await readFile(f); ES2017
?? et ?. process.env.PORT ?? 3000 ES2020

Dans la vraie vie : tous les jours pour const, let, les fonctions fléchées et les fermetures ; var ne s'écrit plus ; call et apply se lisent surtout dans du code ancien ; une erreur « Cannot read properties of undefined » vient souvent d'un this perdu.

Environnement et npm

Installer Node.js

Le concept

Les postes du cours sont prêts. Pour vos projets, quatre façons d'installer Node.js :

  • l'installeur officiel (nodejs.org) : le plus simple, celui du cours sous Windows ;
  • un gestionnaire de versions (nvm sous macOS et Linux ; nvm-windows, fnm ou volta sous Windows) : plusieurs versions côte à côte, pour passer d'un projet à l'autre ;
  • le gestionnaire de paquets du système (apt, brew, winget) : serveurs et intégration continue ;
  • Docker (node:22-alpine) : la production.

Un fichier .nvmrc à la racine du projet contient le numéro de version ; nvm use le lit tout seul. On le crée au TP 1.1.

Dans la vraie vie : une fois par poste ; un développeur qui passe d'un projet à l'autre prend un gestionnaire de versions, et en production Node.js arrive dans une image Docker.

REPL, scripts et premier programme

Le concept

Le REPL (Read, Eval, Print, Loop) est une calculatrice à JavaScript : on tape node, puis une ligne ; Node la lit, l'exécute, affiche le résultat et recommence. Il sert à essayer une ligne ; .exit pour sortir. Un vrai programme s'écrit dans un fichier, lancé avec node fichier.js. Un script reçoit :

  • ses arguments dans process.argv : [0] est le programme node, [1] le script, [2] le premier argument utile ;
  • ses variables d'environnement dans process.env : c'est par là qu'on donne au programme sa configuration (le port, l'adresse de la base) sans toucher au code.

L'objet global s'appelle globalThis ; process, console, setTimeout, fetch et URL sont disponibles sans import.

Commande Effet
node Ouvre le REPL (.help, .editor pour plusieurs lignes, .exit)
node app.js Exécute un script
node --watch app.js Relance à chaque modification (natif depuis Node 18.11)
node --env-file=.env app.js Charge un fichier de variables d'environnement (natif depuis Node 20.6)
node --inspect app.js Débogage (Chrome DevTools, VS Code)
node -e "..." / node -p "..." Évalue / évalue et affiche

Dans la vraie vie : le REPL de temps en temps, pour essayer une ligne ; node fichier.js et process.env tous les jours : toute la configuration d'une application passe par l'environnement.

npm, package.json et versionnage sémantique

Le concept

Un projet utilise du code écrit par d'autres (des paquets) et doit se réinstaller à l'identique sur n'importe quel poste : c'est le travail de npm. package.json, c'est la liste de courses : « dayjs, version 1.11 ou plus récente ». package-lock.json, c'est le ticket de caisse : exactement ce qui a été installé, jusqu'à la moindre dépendance indirecte ; grâce à lui, toute l'équipe installe la même chose.

Champ de package.json Rôle
name, version Identité du paquet
main Point d'entrée quand quelqu'un fait require('taskflow')
scripts Commandes lancées avec npm run suivi de leur nom (npm run dev) ; start et test n'exigent pas run
dependencies Paquets nécessaires à l'exécution
devDependencies Paquets nécessaires au développement seulement (tests, lint)
engines Versions de Node.js supportées

Versionnage sémantique : MAJEUR.MINEUR.CORRECTIF. Le correctif répare, le mineur ajoute sans rien casser, le majeur peut casser.

Écriture Plage acceptée Usage
5.3.0 Exactement 5.3.0 Verrouillage strict
^5.3.0 de la 5.3.0 jusqu'à la 6.0.0, sans la 6.0.0 Défaut de npm
~5.3.0 de la 5.3.0 jusqu'à la 5.4.0, sans la 5.4.0 Correctifs seulement

Dans Git : package.json et package-lock.json ; jamais node_modules/ (énorme, il se reconstruit avec npm install) ni .env (les secrets ; on versionne .env.example).

Commandes :

  • npm install installe tout ce que décrit package.json ; npm install <paquet> ajoute une dépendance, npm install -D <paquet> une dépendance de développement ;
  • npm ci installe exactement le lockfile : c'est la commande de l'intégration continue ;
  • npm ls affiche l'arbre des dépendances, npm outdated les paquets périmés, npm audit les vulnérabilités connues ;
  • npx <outil> lance un outil sans l'installer.

Dans la vraie vie : tous les jours ; npm install, npm run dev, le lockfile dans Git, npm ci sur les serveurs d'intégration continue ; pnpm et Yarn reposent sur les mêmes idées.

Les modules : CommonJS et ES Modules

Le concept

Un module, c'est un tiroir étiqueté : on range dans un fichier le code d'un sujet, et on ne montre aux autres que ce qu'on choisit d'exporter. Le reste du fichier reste privé.

Critère CommonJS ES Modules
Syntaxe require / module.exports import / export
Chargement Synchrone, mis en cache Asynchrone
__dirname Disponible import.meta.dirname (Node 20.11 et plus)
await au niveau supérieur Non Oui
Activation Par défaut "type": "module" dans package.json, ou extension .mjs

Le cours utilise CommonJS, la forme d'Express et de Sequelize ; un nouveau projet peut partir en ES Modules (l'extension est alors obligatoire dans les chemins : './tasks.js').

Un module n'est chargé qu'une fois, puis gardé en cache : tous les fichiers qui l'importent reçoivent le même objet. Un module qui garde un état (un tableau, une connexion) le partage donc avec toute l'application.

Avec ./, require cherche votre fichier ; sans ./, une bibliothèque dans node_modules :

Deux pièges : exports = { add } n'exporte rien (écrire module.exports = { add }) ; require('tasks') au lieu de require('./tasks') cherche un paquet.

Dans la vraie vie : tous les jours ; les nouveaux projets partent souvent en ES Modules, beaucoup de code existant est en CommonJS : il faut savoir lire les deux.

Un serveur HTTP en quelques lignes

Le concept

Un serveur web, c'est un guichet : il attend, quelqu'un arrive avec une demande, il répond, puis il attend le suivant. Le port est le numéro du guichet sur la machine. Node.js le fait avec son module http, sans bibliothèque.

http.createServer((req, res) => { … }) crée le serveur : la fonction est appelée à chaque requête (l'événement request). req est la requête qui arrive, res la réponse qu'on construit ; server.listen(3000) ouvre le port.

Objet Propriétés et méthodes utiles
req method, url, headers, lecture du corps par morceaux
res statusCode, setHeader(), writeHead(), write(), end()
server listen(), close(), événements request et error

Chaque requête reçoit une réponse, et une seule : sans res.end(), le client attend sans fin ; deux réponses provoquent l'erreur Cannot set headers after they are sent (d'où un return après chaque réponse). Un port déjà pris donne l'erreur EADDRINUSE.

Dans la vraie vie : rarement à la main ; une API s'écrit avec Express ou Fastify (dès demain), construits sur ce module : req, res, statut et en-têtes restent les mêmes.

Codes de statut et en-têtes HTTP

Le concept

Une application qui appelle votre API ne lit pas le texte des erreurs : elle lit le code de statut. Quatre familles : 2xx ça a marché, 3xx allez voir ailleurs, 4xx la faute du client, 5xx la faute du serveur.

Code Sens Quand l'utiliser dans TaskFlow
200 / 201 / 204 OK / Créé / Sans contenu Lecture, création (avec Location), suppression
301 / 302 / 303 / 304 Redirections / non modifié 303 après un POST de formulaire (Jour 2)
400 Requête mal formée JSON invalide, paramètre invalide
401 / 403 Non authentifié / Interdit Sécurité (accès refusé à un fichier)
404 / 409 Introuvable / Conflit Ressource absente, doublon
413 / 415 Corps trop gros / type non supporté Envois de fichiers
422 Entité non traitable Validation échouée
429 Trop de requêtes Limitation de débit
500 / 503 Erreur serveur / indisponible Bogue, surcharge

En-têtes à connaître : Content-Type (format du corps, pour nous application/json), Content-Length (taille), Location (adresse de la ressource créée), Cache-Control (ce qu'on peut garder en cache).

Dans la vraie vie : tous les jours ; les applications clientes réagissent aux 4xx et la supervision compte les 5xx : un code exact est un contrat entre les équipes.

Asynchrone et événements

Bloquant ou non bloquant : pourquoi l'asynchrone

Le concept

On lance la machine à laver, puis on fait autre chose ; quand elle sonne, on vient étendre le linge. Personne ne reste assis une heure devant le hublot. Node.js fonctionne ainsi : un seul fil exécute le JavaScript, et il ne doit jamais rester planté à attendre.

  • Bloquant : le programme attend la fin de l'opération (readFileSync, une longue boucle de calcul). Pendant ce temps, plus rien ne s'exécute : ni minuteur, ni requête d'un autre client.
  • Non bloquant : on demande l'opération (readFile), on continue, et une fonction est appelée quand le résultat arrive.

Règle : les fonctions …Sync seulement au démarrage du programme (lire une configuration, quand personne n'attend encore), jamais pendant le traitement d'une requête.

Dans la vraie vie : tous les jours ; fichiers, requêtes SQL et appels d'API se font sans bloquer, et « le service ne répond plus, mais le processus tourne » est le symptôme classique d'un blocage.

La boucle d'événements et l'ordre d'exécution

Le concept

À la boulangerie, la vendeuse sert toujours un client jusqu'au bout avant d'appeler le suivant, et les clients prioritaires passent avant la file. La boucle d'événements (event loop) fait pareil : le fil JavaScript exécute une tâche jusqu'au bout, sans jamais l'interrompre, puis prend la suivante, dans un ordre de priorité fixe.

L'ordre, en quatre niveaux :

  1. Le code synchrone, y compris le début d'une fonction async jusqu'à son premier await.
  2. process.nextTick(fn) : « juste après ce que je suis en train de faire », avant tout le reste. Un post-it collé sur la tâche en cours.
  3. Les microtâches : les then / catch des promesses, et la reprise d'une fonction après await.
  4. Les phases de la boucle : minuteurs (setTimeout), entrées/sorties (fichiers, réseau), puis setImmediate(fn) : « au prochain passage de la boucle, juste après les entrées/sorties ».

Les noms trompent : nextTick passe avant setImmediate.

Depuis le programme principal, l'ordre entre setTimeout(…, 0) et setImmediate n'est pas garanti : il dépend du temps que met la boucle à démarrer. On n'écrit jamais de code qui en dépend.

Dans la vraie vie : tous les jours, sans y penser ; on ne programme pas la boucle, on retient cet ordre pour comprendre un bogue, comme un test qui passe sur un poste et échoue sur un autre. nextTick et setImmediate ne s'écrivent presque jamais dans une application (on écrit async/await) : on les croise dans le code des bibliothèques.

Callbacks, promesses et async/await

Le concept

Lire un fichier ou appeler une API se termine plus tard. Il y a trois façons d'écrire « quand c'est fini, fais ceci », de la plus ancienne à celle qu'on écrit aujourd'hui.

1. Le callback : on donne une fonction à Node, il l'appelle à la fin. C'est comme laisser son numéro : on vous rappelle. Convention de Node, dite error-first : le premier argument est l'erreur (null si tout va bien) ; on la teste en premier et on sort avec return. Défaut : plusieurs opérations à la suite s'imbriquent les unes dans les autres, et le code part vers la droite.

2. La promesse : un objet qui représente un résultat à venir, comme le ticket de pressing qu'on reçoit tout de suite. Elle est d'abord en attente, puis tenue (le résultat est là) ou rompue (une erreur), et ne change plus ensuite. La suite s'écrit dans .then() ; un seul .catch() à la fin attrape l'erreur de n'importe quelle étape.

3. async / await : la même promesse, écrite de haut en bas. await attend le résultat sans bloquer le serveur, et try/catch attrape les erreurs. C'est ce qu'on écrit aujourd'hui. Une promesse rejetée sans catch arrête le programme : on met toujours un catch ou un try/catch.

Pour lancer plusieurs opérations en même temps :

Méthode Résultat
Promise.all toutes réussies, sinon une erreur dès que l'une échoue
Promise.allSettled attend toutes et donne le résultat de chacune
Promise.race la première terminée
Promise.any la première réussie

Pour moderniser une vieille fonction à callback, util.promisify la transforme en fonction qui renvoie une promesse.

Dans la vraie vie : async/await et Promise.all tous les jours ; les callbacks surtout dans le code ancien.

EventEmitter : découpler le métier de la journalisation

Le concept

Une newsletter : l'auteur publie, les abonnés reçoivent, et l'auteur ne sait pas qui est abonné. Un EventEmitter fait la même chose dans le code : il émet un événement (emit), et les écouteurs inscrits sous ce nom (on) s'exécutent. Celui qui émet ne connaît pas ceux qui écoutent : on ajoute un journal, une notification ou des statistiques sans modifier l'émetteur.

Méthode Effet
on(evt, fn) inscrit un écouteur
once(evt, fn) inscrit un écouteur pour une seule fois
off(evt, fn) retire un écouteur
emit(evt, ...args) déclenche l'événement : les écouteurs s'exécutent tout de suite, dans l'ordre d'inscription, avant que emit ne rende la main

Une classe hérite d'EventEmitter pour émettre ses propres événements : class TaskService extends EventEmitter. L'événement error est à part : émis sans écouteur, il arrête le programme. On l'écoute donc toujours.

Dans la vraie vie : on écrit rarement son propre émetteur, mais on s'en sert tous les jours (le serveur HTTP, les flux et process émettent des événements) ; pour un seul destinataire fixe, un appel de fonction suffit ; entre plusieurs serveurs, on passe à une file de messages (Redis, RabbitMQ, Kafka).

Fichiers et chemins : fs/promises et path

Le concept

Le module fs lit et écrit les fichiers. On utilise sa version à promesses, fs/promises, avec await : readFile, writeFile, appendFile, mkdir, readdir, stat, rename, unlink. Les versions synchrone (readFileSync) et à callbacks servent au démarrage et dans le code ancien.

Le piège, ce sont les chemins. Dire « la deuxième maison à gauche » ne marche que si l'on part du bon endroit : un chemin relatif comme 'data/tasks.json' part du dossier depuis lequel on lance node. On construit donc chaque chemin avec path.join, à partir de __dirname, le dossier du fichier en cours : il reste juste quel que soit le dossier de lancement, sous Windows (\) comme sous Linux (/).

Fonction Exemple Résultat
path.join path.join('/srv', 'taskflow', '..', 'public') /srv/public
path.resolve path.resolve('data', 'tasks.json') chemin absolu depuis le dossier courant
path.basename path.basename('/a/b/app.js', '.js') app
path.extname path.extname('photo.png') .png
path.dirname path.dirname('/a/b/app.js') /a/b

require.main === module est vrai quand le fichier est lancé avec node, faux quand il est importé : le même fichier sert de script et de module.

Dans la vraie vie : souvent, pour la configuration, les exports et les fichiers envoyés par les utilisateurs, toujours avec fs/promises et path.join ; les données de l'application vont dans une base (demain).

Les flux : traiter un gros fichier

Le concept

Un flux (stream) traite les données par morceaux, comme un tuyau : un morceau entre, il est transformé, il ressort, et le suivant arrive. Le fichier n'est jamais chargé en entier : seuls quelques morceaux de 64 Ko sont en mémoire à un instant donné.

Quatre sortes de flux : en lecture (Readable, comme fs.createReadStream), en écriture (Writable, comme fs.createWriteStream), dans les deux sens (Duplex, comme un socket réseau) et de transformation (Transform, comme zlib.createGzip). pipeline (module node:stream/promises) les branche bout à bout, attend la fin de tout le trajet et signale l'erreur de n'importe quelle étape. Si l'écriture est plus lente que la lecture, la lecture ralentit d'elle-même : c'est la contre-pression, rien ne déborde.

Dans la vraie vie : de temps en temps ; on s'en sert sans le savoir (req et res du serveur HTTP, téléchargements, envois de fichiers) et on en écrit pour les gros fichiers : exports CSV, archives, journaux.
